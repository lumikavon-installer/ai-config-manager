# Core design and storage contract

The Rust core owns credential access for the desktop and local agent. The frontend receives only a masked presence flag; trusted local SDKs may explicitly request a credential-bearing snapshot through the authenticated socket. `None` in a save request preserves the saved credential; an explicitly supplied empty credential is invalid for OpenAI and is the normal no-auth value for the three local endpoints. Revisions hash exact bytes, while history hashes normalized complete YAML semantics after decryption. Mapping keys are sorted and encryption nonces are excluded from semantic hashes. Explicit nulls and numeric/string types remain distinct. Only a single YAML document, string mapping keys, and untagged values are accepted. Duplicate keys and malformed input are rejected without echoing parser excerpts.

## Model endpoints

`ai.openai` remains the default chat endpoint. `ai.embedding`, `ai.laya`, and `ai.cosyvoice` are independent sibling blocks with the same `base_url`, `model`, and `api_key` fields. Saving one block preserves every other block and unknown YAML values. OpenAI requires a nonempty credential; the three local endpoints accept an empty credential, which is stored as an empty string and sends no `Authorization` header. Missing named blocks are reported as `configured: false` by reads, while decrypted reads, validation, and tests require a configured block (`INVALID_CONFIG`). Every save still compares the whole-file raw revision, so a revision read from any endpoint guards the complete file.

`Store::load_endpoint`, `with_endpoint`, `save_endpoint`, `validate_endpoint`, and `test_endpoint_kind` expose the four blocks; the original methods delegate to OpenAI. History diffs for named blocks use `embedding.base_url`, `laya.model`, `cosyvoice.api_key`, and related names so a flat history remains attributable; OpenAI keeps its legacy unprefixed names. Portable sync exports every configured block with plaintext credentials and re-encrypts each nonempty key on import according to the local encryption policy. A named block with an empty key stays empty and never creates an `ENC(...)` value.

The process takes an OS advisory exclusive lock before reading or writing, checks an exact-byte revision, and atomically replaces a same-directory staged file. All cooperating clients use the same lock. A noncooperating external writer is checked again immediately before replacement, but cannot be made transactionally cooperative by a filesystem API. Symlinks are rejected at file and ancestor boundaries. Files are restricted to the current account (0600 on Unix; protected current-user DACL on Windows). Parent directory symlink races by a malicious actor with write access remain outside the trust boundary; use a private home/config directory.

History contains only redacted field changes and backend-generated semantic SHA-256 values, never a plaintext or encrypted key. A durable pending journal contains the intended revision and next redacted history. Recovery commits history only if the current configuration matches the intended revision, or discards an uncommitted journal when the prior revision still matches. Divergent state blocks saves for manual recovery. Reads of configuration are independent of history health. The ten newest entries are retained. Staged secret files are removed on errors, and any abandoned secret stage is mode 0600.

AES-256-GCM encrypts with a random 96-bit nonce and authenticated versioned associated data. The envelope is `ENC(v1:BASE64(nonce || ciphertext || tag))`. The 256-bit key lives in the native OS credential vault, not in configuration or history. Tests inject an in-memory vault and never access user configuration or the system vault.

## Public API and error handling

`Store::new(PathBuf, Arc<dyn Vault>)` resolves relative paths against the current directory. `load()` returns `ConfigView`; `save(SaveRequest)` uses the desktop source; `save_with_source(request, source)` accepts `desktop`, `cli`, `skill`, or `test`. `save_endpoint(kind, request, source)` selects a named block. `history()` returns newest-first redacted entries. `with_config` calls an in-process closure with a consistent `ConfigSnapshot` containing base URL/model and a `with_secret` accessor; `with_endpoint(kind, ...)` does the same for another block. `with_secret` and `validate_secret` are convenience operations; neither serializes the credential. `test_endpoint()` and `test_endpoint_kind(kind)` perform the explicit `GET {base_url}/models` probe and return only a `ProbeResult`; the lock is released before the network call and the response body is never read into the result. `Vault::get_key` never creates missing keys; `create_key` is only used for encryption. `NativeVault` serializes first creation across configuration paths using a private global lock, then rereads the vault under that lock.

`SaveRequest.encrypt` defaults to `true` when the field is omitted. The GUI, socket protocol and CLI all use encrypted storage by default; plaintext remains an explicit opt-out. The socket-facing `AgentSaveRequest` is deliberately a separate wire type so `SaveRequest` never implements `Serialize`.

## Local agent protocol

The `agent` module exposes a newline-delimited JSON protocol over an AF_UNIX socket (`uds_windows` on Windows), normally at `~/.config/ai-config-manager/agent.sock` and with a deterministic per-user temp fallback for long paths. A random 256-bit token in `~/.config/ai-config-manager/agent.token` authenticates every request. The token file is 0600 on Unix and has a protected current-user DACL on Windows; the socket is 0600 and its directory 0700. Requests are capped at 2 MiB. The operations are `ping`, `read`, `check`, `history`, `test` and `save`; `save` runs the same revision/lock/journal path as the GUI with source `skill`. Successful saves emit a `config-changed` event to the UI. Once a request has been written to a connected socket, a client must not fall back to a direct file write because the original save may have committed with a lost reply. The CLI only falls back when the socket or token is demonstrably unavailable before writing.

`ProbeResult` is `{ ok, status, endpoint, latency_ms, code }`. `code` is one of `ok`, `unauthorized`, `endpoint_unsupported`, `redirect`, `server_error`, `rejected`, `timeout`, `network`, or `client`. The probe uses a 6 s connect timeout, a 15 s total timeout, no redirect following, native TLS roots, and no response-body exposure.

The additional `read_decrypted` operation is an explicit credential read for trusted local SDKs. Its request is `{"version":1,"token":"<agent.token>","op":{"op":"read_decrypted"}}` followed by a newline. After token authentication, `agent::read_decrypted_config` calls `Store::with_config` and returns `{ "ok": true, "data": { "base_url": "...", "model": "...", "api_key": "<plaintext>", "encrypted": true, "endpoint": "openai" } }`. The encryption flag describes the stored API key. All fields come from one validated snapshot; missing or unavailable vault keys fail without recovery key creation. Ordinary `read`, Tauri IPC and CLI output remain redacted. `Secret` and `ConfigSnapshot` do not implement serialization; only the explicit wire response contains the plaintext key. `AgentReply` wipes remaining JSON strings on drop, and HTTP response bodies are zeroized on drop. `into_result` transfers ownership of its credential-bearing value to the caller, which must protect and discard it appropriately. The token grants credential-read access and must only be available to trusted processes of the current OS user.

The JSON socket supports sync configuration, item registration, application registration, policy, record queries, cleanup and execution through the shared `SyncStore`; see [sync-protocol.md](sync-protocol.md) for the extended operations. Concurrent mutations fail with `SYNC_BUSY`; reads remain available. The Rust socket client allows 600 seconds for a sync run. The CLI's `sync-status`, `sync-add`, and `sync` require the running desktop and never fall back to another store. Socket mutations notify the UI through `sync-changed`; refreshes preserve target, registration and policy drafts.

### REST over the local socket

The same AF_UNIX socket accepts HTTP/1.1 in addition to newline JSON. The first request line selects the protocol. REST requests require `Authorization: Bearer <agent.token>` or `X-Agent-Token`; headers and bodies are bounded (16 KiB headers, 1 MiB body), each connection serves one request, and responses are JSON. Endpoints cover `GET /ai-config`, `GET /ai-config/history`, `GET /sync`, `POST /sync/settings`, `POST /sync/items`, `PATCH|DELETE /sync/items/{id}`, and `POST /sync/run`. Request bodies and authorization headers are zeroized on drop. REST is a local, same-user surface; it is not exposed by the webview.

`GET /ai-config/decrypted` exposes the same explicit credential-bearing snapshot as `read_decrypted` and uses the same authentication gate. HTTP responses send `Cache-Control: no-store`. This route is not registered as a Tauri command and is never called by the frontend. The Python SDK supports both direct file/vault reads and authenticated newline JSON over the local socket; socket reads do not fall back to the file or vault on errors.

## GitHub and custom Git sync

`provider` defaults to `github` for existing v1 settings; `git_branch` defaults to `main`. Custom Git invokes the installed client with bounded output/time and interactive prompts disabled. It fetches the selected branch into a temporary bare repository, reads only the encrypted snapshot, and builds a commit preserving other tree entries. No checkout, local hooks, submodules or filters run. A force-with-lease against the fetched head prevents replacing concurrent updates; shared merging retries confirmed conflicts. System credential helpers and SSH agent supply custom Git authentication. Repository tests use a separate empty commit and unique probe branch, delete with a lease and verify removal, without changing settings or reading the AI config. GitHub tests pass the token through scoped environment configuration, never argv or a repository config file. Cleanup failures expose only the residual ref. See [sync-protocol.md](sync-protocol.md).

`SyncStore` persists repository, item/application registrations, policy, deadlines, status and metadata-only records in `sync.json`; the GitHub token and encryption password are separate OS credential-vault entries (`ai-config-manager-sync`). The AI item exports portable YAML with its decrypted key; file items use absolute, regular, non-symlink paths and application items use local socket callbacks, all limited to 1 MiB per item. Bundles use Argon2id (19 MiB, 2 iterations, 1 lane) and AES-256-GCM with a random 128-bit salt and 96-bit nonce, and are stored at `.ai-config-manager/sync.enc` through the GitHub Contents API. Remote response bodies never cross IPC. The decrypted bundle is merged by per-item update time; remote winners apply only to locally registered targets. GUI, JSON and REST expose status and counts without configuration contents or credentials.

Locks time out after five seconds (`LOCK_TIMEOUT`). No lock bypass or force overwrite exists. The caller must reload on `CONFLICT`. A `HISTORY_PENDING` response means configuration replacement succeeded but history finalization remains pending; reload configuration and retry reading history, never assume the save failed. `HISTORY_CORRUPT` blocks writes but not ordinary configuration reads. `KEY_MISSING`, `VAULT_UNAVAILABLE`, and `DECRYPT_FAILED` are distinct. Other codes include `INVALID_CONFIG`, `INVALID_URL`, `INVALID_MODEL`, `INVALID_KEY`, `INVALID_ARGUMENT`, `INVALID_SOURCE`, `UNSAFE_PATH`, `TOO_LARGE`, `ENCRYPT_FAILED`, `AGENT_UNAVAILABLE`, `AGENT_IN_USE`, `AGENT_PROTOCOL`, `AGENT_TOKEN`, `UNAUTHORIZED`, and `IO`. Error messages are fixed strings and never include parser excerpts, raw input, key material, tokens, or OS errors.

The file-size limit is 2 MiB and the accepted value depth is 64. The parser additionally enforces its own recursion and alias-repetition limits. URL length is capped at 8192 bytes, model at 1024, and API key at 65536. Existing overlong field values are summarized, not copied into history; generated history is validated before the configuration commit. YAML comments, styles, and anchor syntax are not preserved, but unrelated accepted values are. Semantic hashes are sensitive equality fingerprints of the complete plaintext configuration, not authentication or signatures; do not publish them. They are stable across map order, encryption toggles, and random nonces, not across substantive scalar-type changes.

All configuration-path ancestors must be actual directories, not symlinks. In particular, on macOS a caller choosing a temporary directory through `/var` should resolve the legitimate directory first (for example, to `/private/var`). The default user-home configuration path normally needs no such adjustment. Windows code is cross-compiled in verification, but native vault/UI/ACL behavior still requires runtime smoke testing on supported Windows/macOS hosts.

Every save writes a fresh random transaction ID as a nonsecret YAML comment and uses the same ID for its history entry. Thus even byte-equivalent plaintext values have distinct raw revisions, while the semantic hash stays unchanged. A journal records the exact prior history-byte hash from the same read that parsed the history. Recovery only installs intended history when the configuration matches the intended transaction and current history still matches that prior hash; already-installed intended history is idempotent. A stale or divergent history/journal pair blocks rather than rolling newer entries back. Pre-replacement and post-replacement failures are covered by synthetic fault injection. If replacement succeeded but a later durability step failed, the result is `HISTORY_PENDING`; if the resulting configuration cannot be identified, the result is `COMMIT_UNCERTAIN`. The latter requires reloading/checking before retrying, not assuming no change occurred.

## Registered applications, scheduling and conflict handling

The extended sync contract is in [sync-protocol.md](sync-protocol.md). `sync.json` also persists policy, the next deadline, up to 100 metadata-only records and an active-attempt journal. New fields have defaults for existing v1 files. Interrupted attempts become one error record on startup. Record pruning is persisted at startup and completion; periodic maintenance also calls `Store::prune_history_before`, which locks and recovers pending configuration transactions before removing expired history. The configuration history's ten-entry cap remains.

Sync is bidirectional for registered, enabled items. The GitHub bundle is authenticated and decrypted before per-item timestamp comparison; equal times use a deterministic digest ordering. Older portable bundles inherit their creation timestamp. Remote-only items survive uploads. Only locally registered paths/interfaces receive remote winners, and local revisions/digests are checked before application. Portable AI imports preserve unknown remote YAML values and local encryption through the same save/journal path. GitHub write races refetch and merge up to three times. The Rust sync client uses a 600-second reply timeout to allow bounded retries and application callbacks.

The Tauri scheduler runs while the process is alive, checks persisted deadlines without accessing credentials, and starts at most one background worker. Before a repository is saved it only advances the deadline instead of recording an attempt. Manual and scheduled attempts share the same mutation lock. An attempt that defers an offline application or hits a transient backend failure schedules a 1-minute backing-off retry (1/2/4/8 minutes, capped at the interval); permanent errors keep the configured interval. Failed scheduled attempts advance the deadline. Shutdown stops scheduling without waiting for a network timeout; an interrupted worker is recovered from its persisted active record next launch. Registered application callbacks use only their own local socket, never manager/GitHub tokens.

A successful AI configuration save writes a private `.dirty` debounce marker next to `ai.yml`. On its next sweep the scheduler promotes that marker into a `pending_sync` request, moves `next_sync_at` to about two seconds ahead, and clears the marker only after the request is accepted (auto-sync enabled, a repository configured, and the AI item enabled for automatic participation). A save that lands while a sync worker is running leaves `pending_sync` set; when the attempt completes, the next deadline is shortened instead of waiting a full interval. This keeps saves prompt without spawning network work inside the save path or bypassing the user's automation settings. The scheduler's single-worker flag and the bundle content/timestamp comparison prevent concurrent or duplicate uploads.

## Native vault identity and durability boundary

The keyring service name is `ai-config-manager`; the account/user label is `config-encryption-v1`. The stored binary secret is exactly 32 bytes. All configuration paths used by this OS account intentionally share that entry; first creation is serialized using `~/.config/.ai-config-manager-vault.lock`. Windows builds select keyring `windows-native`, macOS selects `apple-native`, Linux selects `sync-secret-service` plus `crypto-rust` and `vendored`. No production feature selects the mock provider. Unsupported platforms are not advertised as supported.

A read of existing ENC calls only `get_key`. Missing entries are not recreated. An explicit new API Key can be saved by the user to replace unrecoverable ciphertext, creating a new vault key if no entry remains; this does not recover other files encrypted with the lost key. Back up configuration and the native credential store together. There is no plaintext data-key backup or machine-portable export.

Durability relies on the OS/filesystem honoring file synchronization, same-directory replacement, and directory synchronization where available. Windows uses file flush plus MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH); it does not claim an independently journaled kernel transaction or guarantee against faulty storage hardware. A power loss can still require recovery from backups. The recovery sidecar detects supported interrupted commits; it is not a substitute for backups or an authenticated audit ledger.
